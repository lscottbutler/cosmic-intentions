================================================================================
WHAT THIS APP IS
================================================================================

Cosmic Intentions — a personal goals and visualization web app.
- Users set intentions/goals, then engage with them through timed players
  and an AI-generated execution roadmap (Mission Control).
- Front end is vanilla HTML/CSS/JS — no React, no framework.
- IMPORTANT: there IS now a build step (Vite). The old "no build step" note is dead.

================================================================================
CORE THESIS — THE IDENTITY LIBRARY PATTERN  (this is the heart of the product)
================================================================================

Cosmic Intentions is built on curated "IDENTITY LIBRARIES" — collections of
pre-built "I AM… / I HAVE…" identity cards. This has always been the core thesis.

THE LOOP:
  Browse a Library -> adopt an identity ("I AM a successful negotiator")
  -> work its SHARED, pre-built roadmap -> practice it (visualize / Mind Loop)
  -> discuss it with everyone else working the SAME identity (Cosmic Community).
  The shared curriculum is what makes real community possible — you can't have a
  conversation if everyone is on a different AI-generated path.

IT IS A SCALABLE PATTERN, NOT A ONE-OFF:
- ENTREPRENEUR LIBRARY is the FIRST: 32 (and growing) designed image cards —
  traits/skills/character an entrepreneur needs (I AM A Successful Negotiator,
  I AM Disciplined, I HAVE A Strong Work Ethic, I AM A Great Sales Person, ...).
  Assets: images/ (ENT *.PNG); shown via `ent-slideshow`; backend
  netlify/functions/_entrepreneur-library.js.
- FUTURE libraries: Athlete, Artist, Parent, etc. Adding a card OR a whole
  library = adding a data entry + an image. BUILD FOR TRIVIAL EXTENSION.

LIBRARY ITEMS ARE FIXED, CURATED ASSETS — NOT AI, NOT DRILLABLE:
- Each card = image + fixed "I AM" identity + ONE shared roadmap the team authors.
- Read-only and IDENTICAL for every user. NO per-user AI drill-down (that stays
  only for the user's OWN personal goals — two clearly different modes). Reuse the
  roadmap LOOK, but locked.
- ADOPTABLE: a user can adopt a Library card as one of their intentions (to
  visualize/loop) while keeping the SHARED roadmap. Ties the Library to the core
  app without breaking "everyone is on the same page."
- Store as plain data the owner controls, so it is a true fixed asset.

EACH CARD = A CURATED "MINI DIGITAL EBOOK", ONE PAGE. This curation is the MOAT
(generic AI can't cheaply copy it). Template per card:
  1) Identity ("I AM a Successful Negotiator") + art card.
  2) Owner-curated ROADMAP bullets (he chooses all the text — the spine).
  3) SYNERGY-PARTNER content — links to podcasts, YouTube channels, audio clips,
     interviews with real successful entrepreneurs.
  4) GENERATED from the above: the beliefs, affirmations, winning attitudes, traits
     to internalize.
Content behind each card = BOTH written roadmap AND partner media AND generated
affirmations — not one or the other.

*** SYNERGY PARTNERS — DEEP PIN (first-class business + content lever). Two kinds:
  (a) CONTENT partners (podcasts/creators/channels): send them traffic, they lend
      credibility + content (affiliate / cross-promo).
  (b) BRAND partners: supply product IMAGERY/products for cards + sponsorship
      (free assets + revenue).
Design cards so partner links + imagery are structured data, easy to attach/swap.

CELEBRITY ROADMAPS = a parallel library type ("Joe Rogan's advice to entrepreneurs
who want to…", a whole library, partner-backed). NON-NEGOTIABLE RULE (owner fears
frivolous lawsuits): must be REAL, SOURCED, ATTRIBUTED clips/quotes with links
("in his own words -> watch"), NEVER fabricated advice or implied endorsement.
The sourcing IS the synergy link. Wrong = right-of-publicity / defamation risk.

COSMIC COMMUNITY (forum) — the payoff of shared content. It must NOT become a
spam/negativity temple. Design positivity IN, do not just moderate:
- Members-only (paywalled) = biggest spam/troll filter.
- Structured prompts, not an open wall ("share a win", "where are you stuck?",
  "how did you apply step 3?"). Structure kills ranting.
- Positive-only reactions (encourage/heart, no downvotes).
- AI positivity filter — OpenAI screens every post for negativity/spam/attacks
  BEFORE it publishes (on-brand automated bouncer).
- One discussion thread per trait so talk converges on the shared roadmap.

BUILD SEQUENCE (agreed): Library FIRST (stands alone, immediately valuable),
community layered on later once there is something to talk about.
OPEN QUESTIONS: content behind each card (written roadmap vs video vs both);
community in-house on Supabase vs bolt-on (Circle/Discord); paid-only (leaning yes).

ARCHITECTURE (CURRENT — post ES-module rebuild)
================================================================================

Entry:        index.html (now ~750 lines) loads ES module /src/main.js
Boot order:   src/main.js imports sentry.js FIRST, then styles, then every
              shared/*.js module, then app.js, THEN calls _app_js.init().
              The init() call is deliberately LAST — fixes a circular-import bug
              where init fired before sibling module data existed. Don't reorder.
App logic:    app.js (root, ~3150 lines) — main dashboard behavior
Shared modules (shared/*.js, all ES modules):
  api.js, content-bank.js, activity.js, card-builder.js, mission-control.js,
  weekly-focus.js, today.js, player-launcher.js, the-map.js
Inline onclick= handlers are still used this phase: main.js copies named handler
  functions from the modules onto window[...], and a "handler-tripwire" loudly
  logs (and shows a red bar on localhost) if any handler failed to wire. If you
  add a new inline onclick, add its name to the HANDLERS list in src/main.js.

Other notes:
- No server-side app code. Netlify Functions are the only server code.
- Supabase handles auth + postgres. Check existing schema before adding tables.
- Google Sheets is a data source, not a DB replacement.
- Netlify function timeout is a real constraint — Mission Control generates 50
  items per call and appends on the next call to stay under the limit.

================================================================================
DEFINITION OF DONE — VERIFY, DON'T CLAIM (NON-NEGOTIABLE)
================================================================================

The live site caches and deploys can silently fail. NEVER judge a change by the
live site, and never say something "works" or "is live" without proof.
1. LOCAL = SOURCE OF TRUTH. Run the change locally (npm run dev / preview) and
   load the affected page there.
2. PROVE IT RENDERS. Standalone page → headless screenshot and actually look.
   Auth-gated page (index.html) → say plainly "could not verify — needs login".
3. AFTER PUSHING, CONFIRM THE DEPLOY. `bash scripts/deploy-status.sh` — newest
   Netlify deploy state MUST be `ready`. If error/skipped, it is NOT live — STOP,
   don't keep pushing into a failing pipeline.
4. One change → verify → report. No batches of hopeful commits.
5. State the evidence ("verified on localhost", "deploy <hash>: ready"). If you
   couldn't verify something, say exactly what you couldn't verify.
If you can't prove it, the honest answer is "not verified yet" — never "done".
